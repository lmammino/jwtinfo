# Releasing jwtinfo

The canonical release trigger is a version tag pushed to GitHub. The
[Release workflow](.github/workflows/release.yml), generated by cargo-dist,
builds binaries and installers and publishes the release. Creating a GitHub
release manually or running `cargo publish` locally is not the normal path.

## Prepare the release

1. Confirm that every intended change is on `main`. For stacked PRs, check
   the source repository as well as the branch name: identically named
   branches in a fork and the upstream repository are different branches.
2. Set the package version in `Cargo.toml` and update its entry in
   `Cargo.lock`. Finalize the matching version's dated entry in
   `CHANGELOG.md`, including breaking changes and known limitations.
3. Check the README against the release, then merge the preparation PR.
4. Wait for CI on the exact `main` commit to pass. The tag-triggered release
   workflow does not depend on the separate Rust test workflow.
5. Confirm the publishing credentials are available: `CARGO_TOKEN` for
   crates.io and `HOMEBREW_TAP_TOKEN` for `lmammino/homebrew-tap`. npm uses
   trusted publishing through GitHub Actions OIDC, configured in the npm
   package settings for this repository and `release.yml`; it does not use an
   `NPM_TOKEN`. GitHub release operations use `GITHUB_TOKEN`.

Local checks, from a clean checkout of the release commit:

```bash
cargo test --locked
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo fmt --check
```

## Publish

Ensure the tag matches the package version and does not already exist. For
version 0.7.0, after the preparation steps above:

```bash
git switch main
git pull --ff-only origin main
git status --short
git tag -a v0.7.0 -m "Release v0.7.0"
git push origin v0.7.0
```

Pushing the tag starts publishing. Push only the intended release tag.

The workflow builds the targets and installers listed in
[dist-workspace.toml](dist-workspace.toml), then creates the GitHub release
with generated notes and assets. It subsequently publishes the npm package,
updates the Homebrew formula, and invokes the reusable
[crates.io publishing workflow](.github/workflows/cargo-publish.yml).

## Verify completion

Check the Release workflow for the tag, including all three publishing jobs.
A visible GitHub release alone does not mean the package publishers succeeded.
Confirm the version and assets on GitHub, crates.io, npm, and the Homebrew
tap, then smoke-test an installed binary with `jwtinfo --version` and a
sample token.

If a job fails after another destination has published, inspect the failed
step and retry only what is appropriate. Do not move a published tag or
assume that publishing an existing package version again is supported.

The release workflow is generated. Change cargo-dist settings in
`dist-workspace.toml` and regenerate with the pinned cargo-dist version
(currently 0.32.0) when modifying the release pipeline.
